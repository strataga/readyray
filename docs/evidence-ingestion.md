# Evidence ingestion status and limits

The evidence package validates ZIP archives supplied as bytes. Its intake use case requires the in-memory Secretlint scanner before accepting an archive and calls storage only after every file passes validation and scanning. Authenticated workspace members can submit a raw `application/zip` body to `POST /v1/workspaces/{workspaceId}/evidence/archives`, then retrieve the accepted manifest and digests from `GET /v1/workspaces/{workspaceId}/evidence/archives/{intakeId}`. The PostgreSQL adapter stores accepted archive bytes and metadata together in one insert; inventory reads select metadata only. There is no GitHub importer yet, and the database-backed upload and inventory flow has not been exercised against a running PostgreSQL instance.

The initial ZIP policy rejects input over 50 MiB compressed, more than 250 MiB of expanded regular files, more than 5,000 entries, unsafe or colliding paths, symlinks and other special file types, encrypted entries, unsupported compression, and checksum or size mismatches. It caps path complexity and processes one archive at a time per Node.js process. HTTP admission checks the session and workspace membership before buffering and limits each API process to one active upload. No archive member is executed or extracted to disk.

The reader reports normalized file paths, sizes, and SHA-256 digests. It accepts an awaited per-file scanner callback, verifies that the callback did not change the hashed bytes, and clears its temporary file buffer afterward. The current scanner rejects binary-like or malformed UTF-8 content and text files above 8 MiB. It uses Secretlint's recommended rules without evidence-controlled suppression comments. Secret scanning is heuristic; it cannot prove that no secrets remain. The intake use case requires the scanner before calling storage and rejects scanner failure. Public GitHub ingestion must pin a commit SHA and apply the same content limits and scanning rules.

The limits are code defaults for this early slice. Before prerelease, validate them with hostile archive tests, a PostgreSQL-backed upload run, concurrent-load evidence, and a complete secret-scanning and recovery path.
